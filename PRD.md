# PRD — Evidence Factory

Status: Draft. **Not yet published to an issue tracker** — no tracker / triage-label vocabulary is configured for this repo (`/setup-matt-pocock-skills` has not been run). Apply `ready-for-agent` triage when the tracker is wired in.

## Problem Statement

A vendor or team showcasing an AI digital-evidence analysis system needs realistic, large evidence corpora to demonstrate the AI "cracking" a case. The corpora must look like the real disclosures forensic AI consumes (per-custodian device data, valid file formats, plausible metadata, chain-of-custody manifests) and must contain a *hidden* narrative reconstructible only by aggregating many weak signals across many artifacts — not a single damning file. Today, that means hand-curating a demo case or scraping real disclosures, both of which are slow, narrow, and legally fraught. Live demos stall on "is this just a cherry-picked example?" because operators have no way to produce a fresh, defensible, machine-checkable case on demand from a story they can point at.

## Solution

Evidence Factory is a Python web app that takes a source story (a URL, an uploaded text file, or pasted text — known court cases, public-domain novels like Sherlock Holmes, or anything in between) and produces a downloadable evidence corpus packaged like a real forensic disclosure, together with a sealed answer key.

The story's setting/era stays as written (Baker Street, Victorian London is fine) — only the *container media* are modernised. A Victorian will becomes a PDF, a telegram becomes an SMS, an alibi letter becomes an email. The corpus is organised into per-custodian / per-device folders with original-style filenames and a chain-of-custody manifest CSV (acquisition time, owner, device, SHA-256). Every artifact is born from a specific persona's device or system through a profile that produces genuinely valid bytes with real metadata (real RFC822 email headers, real EXIF on photos, real PDF structure, real SQLite app DBs, real CSV logs, real `.xlsx` ledgers).

Behind the scenes, an LLM derives the canonical truth of the case from the source, expands it into a granular validated event graph, and emits load-bearing artifacts whose signals corroborate a proposition graph. A smoking-gun critic LLM gates every load-bearing artifact: anything strong enough to solve the case alone is split, diluted, redacted-and-relocated, or demoted to a refuted red herring (strategy chosen per-instance). Red herrings are refuted by construction — each carries a breaker bundle that conclusively kills it, and the bundle itself must survive smoking-gun critique. The bulk of the corpus is haystack noise generated by a cheap model, batched and persona/timeline-consistent, written through the same valid-byte profiles so it is indistinguishable from signal at the surface. A global closure check verifies that the true account is corroborated above threshold and remains the uniquely best-supported explanation before packaging.

The deliverable is a single zip with `/corpus` (what the operator hands to the AI under test) and a separately sealed `/SOLUTION` pack (truth outline, proposition graph, signal ledger, red-herring → breaker map, per-artifact provenance truth) that the operator keeps. Scoring is out of scope for v1 — that is the consumer's concern.

## User Stories

Actors: **Demo Operator** (showcases an AI digital-evidence analyser), **Source Author** (chooses and submits the source story), **Audience** (watches the demo; sometimes is the consumer's prospective buyer or the AI under test), **AFK Engineer** (the human watching the autonomous implementation harness).

1. As a Demo Operator, I want to generate a fresh evidence corpus from any source story I point at, so that I can demonstrate the AI on cases the audience can verify aren't cherry-picked.
2. As a Demo Operator, I want to submit a story by URL, by uploaded text file, or by pasted text, so that I am not constrained to a single intake mode.
3. As a Source Author, I want the app to fetch a public URL and extract the readable story content for me, so that I do not need to clean up navigation, ads, or boilerplate by hand.
4. As a Demo Operator, I want known court cases and public-domain novels (Sherlock Holmes, etc.) to be valid sources, so that I can pick narratives the audience already recognises.
5. As a Demo Operator, I want the story's era and setting preserved as written, so that a Holmes corpus still feels like Holmes — only the file formats are modernised.
6. As a Demo Operator, I want every artifact delivered in a real modern file format (`.eml`, `.csv`, `.pdf`, `.xlsx`, `.jpeg`, log/CSV) with valid bytes, so that the consumer AI's format/metadata parsers behave exactly as they would on a real seizure.
7. As a Demo Operator, I want each artifact to have a specific persona owner and a specific device/system of origin, so that provenance is a first-class signal the AI can analyse.
8. As a Demo Operator, I want photos to carry valid EXIF (including timestamps and, where appropriate, GPS), emails to carry valid RFC822 headers, PDFs to carry sensible document metadata, and `.xlsx` files to carry author/created/modified metadata, so that the corpus survives forensic scrutiny.
9. As a Demo Operator, I want the corpus organised into per-custodian/per-device folders with original-style filenames, so that the layout matches what the AI sees in a real disclosure.
10. As a Demo Operator, I want a chain-of-custody manifest CSV listing acquisition time, owner, device, file path, and SHA-256 for every artifact, so that the demo includes the same control surface real investigators rely on.
11. As a Demo Operator, I want a sealed `/SOLUTION` pack delivered alongside `/corpus` but clearly partitioned, so that I can hand the AI only the corpus without leaking the key.
12. As a Demo Operator, I want the sealed pack to include the truth outline, the proposition graph, the signal ledger, the red-herring → breaker map, and the per-artifact provenance truth, so that I can adjudicate any answer the AI returns at proposition granularity.
13. As a Demo Operator, I want the corpus and sealed pack delivered as a single zip download with a clear top-level split, so that distribution is a one-click operation.
14. As a Demo Operator, I want generation to be a long-running job with a live progress stream, so that I can see which stage (extraction, event graph, artifact emission, critique, closure, packaging) is currently running.
15. As a Demo Operator, I want generation to recover from transient LLM failures without restarting from scratch where possible, so that long runs are not lost.
16. As an Audience member assessing the AI, I want the corpus to contain hundreds to a thousand-plus artifacts, so that the AI's claim of "finding the needle" is non-trivial.
17. As a Demo Operator, I want a controllable mix of load-bearing artifacts (signal, red-herring, breaker) and pure haystack noise, so that I can tune the difficulty per audience.
18. As a Demo Operator, I want no single artifact to be strong enough to solve the case on its own, so that the demo cannot be trivially short-circuited by a keyword search.
19. As a Demo Operator, I want every key truth-proposition to be supported by at least N independent corroborating artifacts (across owners/devices/formats), so that the case is provable in aggregate when the AI does the work.
20. As a Demo Operator, I want red herrings that look genuinely tempting, so that the demo showcases the AI's ability to resist false leads.
21. As a Demo Operator, I want every red herring to be refutable from the corpus by a designated breaker bundle, so that there is always a defensible "this is why it isn't X" answer.
22. As a Demo Operator, I want the same six core file profiles (email, SMS/chat export, PDF, `.xlsx` ledger, JPEG+EXIF photo, log/CSV) to cover both load-bearing and noise artifacts, so that an AI cannot trivially separate signal from noise by file type alone.
23. As a Demo Operator, I want haystack noise to be persona- and timeline-consistent, so that a careful AI examining ownership and time still sees a coherent universe of activity.
24. As a Demo Operator, I want noise generation to be cheap so that scaling to 1000+ artifacts is affordable, even though every noise artifact is LLM-authored.
25. As a Demo Operator, I want a guard that prevents noise from accidentally leaking a true proposition or contradicting the truth, so that haystack does not break the case.
26. As a Demo Operator, I want a synthetic-evidence disclaimer field stamped into artifact metadata and the manifest, so that the corpus is identifiable as fabricated when it leaves my hands.
27. As a Demo Operator, I want an operator attestation gate before generation begins (acknowledging authorised use of any real-people / in-copyright source), so that responsibility for source choice is recorded.
28. As a Demo Operator, I want the model used for reasoning roles (extraction, event graph, content, critic, closure) to be Claude Opus 4.7 or Sonnet 4.6, and the model used for bulk noise to be Claude Haiku 4.5, so that quality and cost are appropriate to the task.
29. As a Demo Operator, I want prompt caching used for persona / timeline / case-bible context across many calls, so that per-case cost is bounded.
30. As a Demo Operator, I want noise generation batched (many artifacts per call), so that scaling does not multiply API round trips.
31. As a Demo Operator, I want each load-bearing artifact (or small group) to be critiqued by a smoking-gun judge, so that a single strong file never slips through.
32. As a Demo Operator, I want the generator to react to a smoking-gun flag by picking — per instance — one of: split across artifacts/owners, dilute in place, redact-and-relocate, or demote to a refuted red herring, so that strong signals are defused in organically varied ways.
33. As a Demo Operator, I want a bounded retry on the critic after remediation, so that the generation loop terminates.
34. As a Demo Operator, I want a final closure check after all remediation, so that propositions weakened below threshold by splitting/redacting are topped up with more weak corroborators before packaging.
35. As a Demo Operator, I want generation to fail loudly with a diagnostic if closure cannot be reached, so that I do not ship an unsolvable corpus by mistake.
36. As a Demo Operator, I want each run to produce a fresh unique corpus from the same inputs, so that the same source can be reused without producing identical demos.
37. As a Demo Operator, I want the app to run locally or as a small internal service, so that no source content has to leave my environment except for LLM calls.
38. As an AFK Engineer, I want a sandcastle-based AFK harness (`scripts/sandcastle/orchestrate.ts` + `sandbox.Dockerfile` + `.sandcastle/.env`) configured for this repo's slice DAG, so that the implementation work can be executed by autonomous Claude Code agents in parallel sandboxes after the issues are filed.
39. As an AFK Engineer, I want the harness to use spine-serial / apron-parallel scheduling, a Phase-1 implementer agent + Phase-2 UI-tester gate, resume-via-closed-issues, worktree reclaim, and preflight checks for repo-root cwd and Claude/GH credentials, so that the proven agentic-ai harness pattern works here unchanged.

## Implementation Decisions

### Pipeline shape (derive-then-decorate)

Source intake → truth extraction → operator attestation gate → event graph → load-bearing artifact emission → smoking-gun critique with random-strategy remediation → red-herring + breaker design → haystack noise generation → global closure check → packaging.

### Architecture & deployment

- **Backend:** Python + FastAPI. Format-writer ecosystem (Pillow/piexif, reportlab/pikepdf, openpyxl, eml/email libs, SQLite for app DBs, hashlib) lives natively here.
- **Front end:** Light SPA (vanilla or minimal React — final choice deferred to implementation). Three intake modes (URL fetch, file upload, paste), progress stream, zip download. Operator attestation gate is a front-end step.
- **Run shape:** Long-running async job + progress stream (SSE or WebSocket). Local or small internal hosting.
- **LLM:** Claude tiered via Anthropic SDK with prompt caching. **Opus 4.7 / Sonnet 4.6** for reasoning roles (extraction, event graph, artifact content, smoking-gun critic, red-herring designer, closure solver). **Haiku 4.5** for batched haystack noise. Single SDK; tiering encapsulated by the LLM Gateway module.

### Modules

Deep modules (no LLM — pure / deterministic interfaces, strongest test candidates):

1. **Closure Verifier.** Input: proposition graph + signal ledger + red-herring breaker map. Output: pass/fail + gap report (which propositions are under-supported, which red herrings are insufficiently refuted, which dominance margins fail). Pure logic. The correctness backbone of the entire pipeline.
2. **Provenance Catalog.** Six profile writers behind a single `ArtifactWriter` interface: `write(payload, provenanceContext) -> {path, bytes, metadata}`. Profiles: `Email .eml` (RFC822 headers via Python `email`), `SMS/chat export` (CSV and/or SQLite), `PDF document` (reportlab/pikepdf with doc metadata), `.xlsx ledger` (openpyxl with author/created/modified), `JPEG photo` (Pillow + piexif EXIF including timestamps and optional GPS), `log/CSV` (access logs / call detail records). Profiles also expose a metadata schema and an owner/device binding contract. Real-library byte generation; no LLM inside the profile itself.
3. **Signal Ledger.** Data structure binding artifact → proposition(s) → signal weight, with queries for independence (distinct owners / devices / formats), corroboration count per proposition, and contradicted-proposition tracking. Pure data.
4. **Packager.** Assembles `/corpus` as a forensic disclosure (per-custodian / per-device folders, original-style filenames, chain-of-custody manifest CSV with acquisition time, owner, device, path, SHA-256). Assembles the sealed `/SOLUTION` pack (truth outline, proposition graph, signal ledger, red-herring → breaker map, per-artifact provenance truth). Guarantees separation: nothing from `/SOLUTION` may appear in `/corpus`. Emits a single zip. Stamps the synthetic-evidence disclaimer field into per-artifact metadata and the manifest.
5. **Source Intake.** `ingest(input: URL | UploadedFile | RawText) -> SourceText`. URL path: fetch + readability extraction; file path: decode + normalise; paste path: trim + normalise. Returns a clean, normalised body the rest of the pipeline can treat uniformly. No LLM.
6. **Remediator.** Applies one of the four strategies — split / dilute / redact-relocate / demote-to-red-herring — to an artifact (or artifact group) flagged by the critic. The strategy *selector* is injectable; the *transforms* themselves are deterministic given a strategy and a candidate artifact. The split path produces N weaker fragments distributed across different owners/devices/formats; demote produces a false-but-tempting alternative proposition and registers the need for a breaker bundle.
7. **Persona & Device Registry.** Actors → personas → owned devices/accounts → permitted profile set. Enforces "only persona P with device D can emit profile X" so provenance is internally consistent. Pure data + simple queries.

LLM-backed modules (contract-tested for schema validity and invariants, not exact output):

8. **LLM Gateway.** `complete(role, prompt, options) -> response`. Encapsulates model routing (Opus/Sonnet vs Haiku per role), prompt caching, batching for noise (many noise artifacts per call), retries on transient errors, and structured-output schema enforcement. The single integration point with the Anthropic SDK.
9. **Truth Extractor.** SourceText → CanonicalTruth ::= { prose outline, proposition graph }. Proposition graph is a set of discrete, checkable propositions ("X was at location L at time T", "A wired £S to B", etc.) plus their relations (causal, contradictory, supports, requires).
10. **Event Graph Builder.** CanonicalTruth + DifficultyParams → validated EventGraph. Events are timestamped, located, attributed to actors, and bound to propositions they can carry. Validation rules enforce timeline coherence and persona consistency before downstream emission.
11. **Artifact Emitter.** For each event in the graph: produces load-bearing artifact briefs (content + provenance context + signal weight + bound propositions), invokes the Provenance Catalog writer for the matching profile, and records the result in the Signal Ledger.
12. **Smoking-Gun Critic.** `critique(artifact | small group, CanonicalTruth) -> { tooStrong: bool, reason }`. Batched where possible. Verdict triggers the Remediator.
13. **Red-Herring & Breaker Designer.** Given the canonical truth and the current load-bearing set, designs plausible false propositions, attaches weak supporting artifacts (registered as red-herring signal), and designs a **breaker bundle** that — in aggregate, not individually — conclusively refutes the false proposition. Each breaker artifact must itself pass the Smoking-Gun Critic, so breakers are typically fragmented (e.g. an alibi SMS + a badge log row + a photo with EXIF GPS together).
14. **Noise Generator.** Cheap-model (Haiku), heavily batched, persona/timeline-consistent. Writes through the same six Provenance Catalog profiles so the surface is indistinguishable from signal artifacts. Includes a cheap batched **leak/contradict guard** check (structural / keyword / micro-LLM TBD at build time) that flags noise which inadvertently restates a true proposition or contradicts the truth; flagged noise is regenerated, not added to the ledger.

Glue:

15. **Pipeline Orchestrator.** FastAPI async job runner: wires stages, streams progress (per-stage status + counts), surfaces a final-state result the SPA can use to trigger zip download. Handles bounded retries on LLM Gateway failures.
16. **Attestation Gate.** Operator attestation step (front-end + persisted in the sealed pack) acknowledging authorised use of the source. Also injects the synthetic-evidence disclaimer field that the Packager stamps into per-artifact metadata.
17. **AFK Sandcastle Harness** *(build-time, not runtime)*. Copied from `agentic-ai/scripts/sandcastle/` and `agentic-ai/.sandcastle/`. Uses `@ai-hero/sandcastle` (mattpocock/sandcastle — note: bare npm `sandcastle` package is unrelated and has a critical lodash advisory; do not use it). Provides:
    - `scripts/sandcastle/orchestrate.ts` — hardcoded slice DAG (spine serial, apron parallel), per-slice implementer prompt builder, Phase-2 UI-tester gate (`<test-result>PASS|FAIL|SKIPPED-NOT-UI</test-result>`), resume-via-closed-issues, host worktree reclaim, repo-root cwd + agent-credentials preflight.
    - `scripts/sandcastle/sandbox.Dockerfile` — Node 22 bookworm base + Python + GitHub CLI + Playwright + Claude Code CLI, AGENT_UID/GID aligned with host.
    - `scripts/sandcastle/package.json` — pinned `@ai-hero/sandcastle`, `tsx`, `typescript`.
    - `.sandcastle/.env.example` — declared (blank) env keyset; real values exported in the shell that runs `npm run go`.

### Correctness invariants the pipeline must hold before packaging

- **Closure (lower bound):** every truth proposition has ≥ N independent corroborating load-bearing artifacts (distinct owners, devices, formats), where N is set by the difficulty parameters.
- **Smoking-gun bound (upper bound):** no single load-bearing artifact, and no breaker artifact, individually proves a key truth proposition or refutes a red herring — every Smoking-Gun Critic verdict is `tooStrong: false`.
- **Refuted-by-construction:** every red herring proposition is refuted by its breaker bundle in aggregate, and the bundle survives smoking-gun critique.
- **Dominance:** the canonical truth proposition graph is the uniquely best-supported account; no contested alternative reaches truth's support level.
- **Provenance consistency:** every artifact's owner / device / profile triple is permitted by the Persona & Device Registry; every metadata field (timestamps, GPS, message IDs, hash links) is consistent with the timeline and the owning persona's device fingerprint.

### Reproducibility

Out — each run is a fresh, unique corpus. "Parametric" means parameterised by source + difficulty inputs, not seedable. No case-bundle re-render path. The sealed `/SOLUTION` pack is still emitted as a deliverable, just not for re-derivation.

### Operator attestation & IP/PII posture (decision recorded)

Real identities are **not** transformed. The operator attests authorised use at the gate. The cheap mitigation that does not touch source fidelity — stamping a "synthetic evidence" disclaimer field into artifact metadata and the manifest — is in scope and is handled by the Attestation Gate + Packager.

## Testing Decisions

### What makes a good test in this codebase

- **Test external behaviour, never implementation details.** A test for the Closure Verifier asserts pass/fail and gap content for a given graph+ledger input — never that internal helpers were called.
- **Pure-logic modules get unit tests with hand-built fixtures.** No LLM mocking is needed for the seven deep modules; their interfaces are pure functions of in-memory data.
- **Provenance Catalog profiles get golden-file tests** that re-parse their own output with a different library where possible (e.g. write a JPEG with Pillow+piexif, re-read EXIF with `exifread`; write an `.eml`, re-parse with `email.parser`) to assert structural validity, not bit-equality.
- **LLM-backed modules get contract tests, not exact-output tests.** Assert that the output validates against the structured-output schema, that invariants hold (critic verdict shape; noise guard never tags a true proposition; event graph timeline is monotone where the truth says so), and — where useful — that the module behaves correctly given a recorded/mock LLM response. Exact prose is never asserted.
- **One end-to-end smoke test** runs the whole pipeline on a small fixed public-domain source and asserts: the deliverable zip has `/corpus` and `/SOLUTION` separated, the manifest hashes match the corpus files, the Closure Verifier passes, and the smoking-gun critic returned `tooStrong: false` for every load-bearing artifact.

### Modules in test scope (decision: all pure deep modules — chosen by operator)

1. Closure Verifier — pass/fail + gap report on hand-built graph+ledger fixtures, including: under-supported proposition, dominated red herring with missing breaker, dominance-margin failure.
2. Provenance Catalog — golden-file structural validity per profile (`.eml`, SMS/chat, PDF, `.xlsx`, JPEG+EXIF, log/CSV); metadata round-trip; SHA-256 stability across two writes with identical payload+context.
3. Signal Ledger — corroboration count, independence (distinct owners/devices/formats), contradicted-proposition tracking.
4. Packager — `/corpus` layout (per-custodian/per-device folders, original-style filenames), manifest CSV correctness (every artifact present, SHA-256 matches), `/SOLUTION` separation (no key file inside `/corpus`), zip integrity.
5. Source Intake — URL fetch with a stubbed HTTP client (readability extraction), uploaded text file decoding (encoding detection), paste normalisation.
6. Remediator — given an injected strategy, the four transforms each produce structurally valid outputs (split yields N weaker, owner-distinct fragments; dilute preserves payload length envelope; redact-relocate removes the flagged span and emits a weaker corroborator elsewhere; demote registers a false proposition + breaker requirement).
7. Persona & Device Registry — permission queries; device-profile binding; cross-actor isolation.

### Modules explicitly **not** in test scope for v1 (out of scope below)

LLM-backed modules (Truth Extractor, Event Graph Builder, Artifact Emitter, Smoking-Gun Critic, Red-Herring & Breaker Designer, Noise Generator, LLM Gateway) and glue (Pipeline Orchestrator, Attestation Gate, AFK Sandcastle Harness) are not in v1 test scope. They will be exercised by the end-to-end smoke test.

### Prior art

Greenfield repo — no in-tree prior art. The Provenance Catalog golden-file pattern is canonical in Python format-library ecosystems (Pillow / piexif / openpyxl / reportlab all have test suites that read back their own output, and that pattern transfers directly).

## Out of Scope

- **Scoring or judging the consumer AI.** No built-in judge, leaderboard, or evaluation harness. Scoring is the consumer's concern.
- **Reproducibility / seedable cases.** Each run is a unique corpus; no case-bundle re-render path.
- **Identity/IP fictionalisation.** Real names, places, and plot specifics are preserved per operator attestation; a fictionalisation layer is deliberately not built.
- **Period-faithful media.** No scanned letters / telegram forms / typed ledgers — present-day file containers only.
- **Modernisation of story content.** No rewriting "hansom cab" to "Uber"; the era of the *story* is preserved.
- **Additional provenance profiles for v1.** No browser-history SQLite, no GPS/GPX track, no messaging-app DB (WhatsApp `msgstore`), no CCTV MP4 stub. Six profiles only.
- **External AI adapters.** The app does not call the consumer AI under test; it only delivers a corpus.
- **Authentication / multi-tenant access.** Local or single-tenant internal use; no user accounts.
- **Reproducible / deterministic LLM output.** No temperature-0 + seed reliance; we accept LLM nondeterminism inside derive-then-decorate, gated by invariants.
- **Unit tests for LLM-backed modules in v1.** Covered only by the end-to-end smoke test.

## Further Notes

### Residual decisions deferred to implementation

- **Source-genre scope.** The six-profile catalog implicitly assumes interpersonal crime/mystery narratives; no explicit genre allowlist is enforced at intake.
- **Concrete difficulty numbers.** The *mechanism* is locked (smoking-gun critic + closure invariants); the numeric levers (corroborators per proposition, fragmentation factor, dominance margin, target artifact count, herring count, presets vs raw knobs) are tuning, set during build.
- **Noise leak/contradict guard implementation.** A cheap batched check is in scope; the exact mechanism (keyword / structural / micro-LLM) is an implementation detail.
- **Front-end framework.** Light SPA — vanilla vs minimal React decided during implementation. The operator-facing flow (intake → attestation → progress → download) is fixed.
- **Attestation UX wording.** The gate exists; exact wording is implementation-time content.

### Risk record (decision logged, not re-litigated)

Operator-attested, no identity transform combined with fabricated evidence about identifiable real people is the highest residual risk in the design. The cheap mitigation that does not touch source fidelity — a synthetic-evidence watermark field stamped into artifact metadata and the chain-of-custody manifest — is in scope (Attestation Gate + Packager). This is the project's documented posture.

### Cost / scale envelope

Cost scales with the **load-bearing** artifact count (~40–150) and the noise count (300–1000+) at Haiku rates with batching and prompt-caching of persona/timeline context — not with total corpus size linearly at top-tier rates. Generation is a long-running job; a typical case should run in minutes, not hours, on a single FastAPI worker.

### Notes on the AFK harness

Sandcastle setup is copied from `agentic-ai` and is **AUTHORED, NOT RUN** until the human checklist is complete (mirroring the agentic-ai runbook §2 pattern):

- `.sandcastle/.env` must exist at repo root with declared (blank) keys; real values exported in the same shell that runs `npm run go`.
- Repo-root cwd is mandatory (the `resolveRepoRoot` gotcha — Windows worktree git-mount chain breaks silently otherwise).
- `CLAUDE_CODE_OAUTH_TOKEN` (or `ANTHROPIC_API_KEY`) and `GH_TOKEN` are preflight-checked before any sandbox launches.
- Sandbox image must be built before `--go`: `docker build -t evidence-factory-sandbox -f scripts/sandcastle/sandbox.Dockerfile .` (rename image from `agentic-v2-sandbox` for this repo).
- Slice DAG is to be authored once the PRD is broken into issues by `/to-issues`. Spine slices = correctness-critical pure modules (Closure Verifier, Provenance Catalog, Signal Ledger, Packager); apron slices = LLM-backed and glue modules.
